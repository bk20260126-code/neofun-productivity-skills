# Claude Cowork Best Practice Skill

## Purpose

이 스킬은 Claude Cowork 워크스페이스를 올바르게 설계하고 지속적으로 최적화하기 위한 공식 SOP(Standard Operating Procedure)다.  
사용자가 이 스킬을 실행하면, Claude는 아래 단계를 따라 워크스페이스를 진단·설계·개선한다.

**트리거 조건:**
- 처음 Cowork 워크스페이스를 세팅할 때
- CLAUDE.md 또는 MEMORY.md를 검토하거나 최적화하고 싶을 때
- Claude Projects에서 Cowork으로 이전(마이그레이션)할 때
- Workstation 또는 Skill을 새로 만들 때
- "Cowork 최적화", "CLAUDE.md 정리", "MEMORY.md 다이어트" 등을 요청할 때
- Rules에 동조 방지·비가역 행동 확인 같은 판단 품질 규칙을 추가하고 싶을 때
- 규칙이 쌓여 상충·중복이 의심될 때 정기 감사를 하고 싶을 때

---

## Skill Workflow

### Step 0 | 컨텍스트 파악

스킬 실행 전, 다음을 확인한다:
1. 사용자의 작업 목적은 무엇인가? (신규 세팅 / 기존 파일 최적화 / 이전 / 스킬·워크스테이션 생성)
2. 기존 CLAUDE.md와 MEMORY.md가 있는가? 있다면 먼저 읽는다.
3. 불명확한 부분이 있으면 단 하나의 질문만 한다.

## SOP 1 | CLAUDE.md 작성 및 최적화

### 1-1. 핵심 원칙: 300줄 규칙

루트 CLAUDE.md는 **매 세션마다 로드**된다. 따라서 파일이 무거울수록 토큰 낭비가 발생한다.

| 기준 | 상태 |
|---|---|
| 200~250줄 | ✅ 이상적 |
| 250~300줄 | ⚠️ 주의 필요, 정리 권장 |
| 300줄 초과 | 🚨 즉시 경량화 필요 |

**경험 데이터:** 600줄 → 250줄로 줄였을 때 토큰 사용량 약 25% 감소.

---

### 1-2. 표준 6섹션 구조

루트 CLAUDE.md는 기본적으로 다음 순서로 구성한다. 다만 **섹션 목록을 채우는 것이 목적이 아니다** —
해당 없는 섹션은 만들지 않고, 필요한 섹션은 추가해도 된다. 지켜야 할 것은 순서가 아니라
**매 세션 로드되는 무게**다:

```
# CLAUDE.md

## Memory System
## Preferences
## Rules
## Routing Map
## References
## Creating New Workstations (→ 추후 외부 파일로 이전 권장)
```

**각 섹션 가이드:**

**① Memory System**
- 세션 시작 시 MEMORY.md를 읽도록 지시
- CLAUDE.md vs MEMORY.md 파일 분류 규칙 포함 (아래 1-3 참고)
- 메모리 시스템 상세 규칙은 별도 참조 파일로 운영 가능

**② Preferences**
- 커뮤니케이션 스타일 (톤, 길이, 포맷)
- 예: "응답은 300단어 이내로 유지", "리스트는 불릿 포인트, 설명은 자연스러운 문단으로"

**③ Rules**
- "always / never" 형태의 행동 가드레일
- 예: "복잡한 작업 전 항상 명확화 질문 먼저", "파일 변경 시 반드시 변경 이유 설명"
- 판단의 질을 다루는 고급 패턴(동조 방지, 비가역 행동 확인 게이트)은 아래 **1-6** 참고

**④ Routing Map**
- 워크스테이션 라우팅 테이블 (아래 형식)
- 새 워크스테이션 생성 시 자동으로 행 추가

```markdown
| Workstation | Route here when I... |
|---|---|
| Email HQ | 이메일 작성·회신·검토 |
| Newsletter WS | 뉴스레터 작성 |
| Research Desk | 리서치·분석 작업 |
```

**⑤ References**
- 온디맨드 로드 파일 포인터 테이블
- 매 세션 로드하지 않고, 트리거 조건 충족 시에만 로드

```markdown
| Resource | Read when... |
|---|---|
| voice-principles.md | 내 이름으로 콘텐츠 작성 시 |
| file-creation-rules.md | 새 파일 생성 시 |
| brand-book.html | 시각물 제작 직전 (색·비율 확인) |
```

**참조 파일의 형식 — 마크다운이 기본이지만 전부는 아니다**

| 참조의 성격 | 형식 | 이유 |
|---|---|---|
| 규칙·절차·체크리스트 | `.md` | 에이전트가 읽고 사람이 편집하기 쉽다 |
| 색·비율·레이아웃·타이포 | `.html` | 마크다운은 **색을 보여주지 못한다.** hex를 나열해도 사람은 지배 비율을 볼 수 없다 |

시각 규칙을 HTML로 둘 때 두 가지를 지킨다.

1. **정본을 이중화하지 않는다.** 규칙의 정본은 하나로 두고 HTML은 그 렌더링임을 파일 안에 명시한다.
   둘 다 정본이 되면 다음 편집에서 조용히 갈라진다.
2. **자기완결로 만든다.** 외부 CDN·웹폰트를 참조하면 오프라인이나 다른 환경에서 깨진다.

**⑥ Creating New Workstations**
- 초기에는 CLAUDE.md에 포함
- 워크스페이스가 성숙해지면 외부 참조 파일로 이전하고 1줄 포인터로 대체

### 1-3. CLAUDE.md vs MEMORY.md 파일 분류 규칙 (핵심)

파일에 항목을 저장할 때 반드시 두 가지 테스트를 적용한다:

| 테스트 | 판단 | 저장 위치 |
|---|---|---|
| **Test 1**: "always", "never", "before X do Y" 등 행동을 지시하는가? | 처방적(Prescriptive) | → **CLAUDE.md** |
| **Test 2**: 내일 바뀔 수 있는 사실(fact/status)인가? | 기술적(Descriptive) | → **MEMORY.md** |

**예시:**

| 항목 | 분류 | 이유 |
|---|---|---|
| "이메일 초안 작성 전 기존 스레드 확인" | CLAUDE.md ✅ | "before X do Y" 행동 규칙 |
| "회사는 Google Workspace 사용" | MEMORY.md ✅ | 변경 가능한 사실 |
| "항상 응답 전 MEMORY.md 읽기" | CLAUDE.md ✅ | always 행동 지시 |
| "현재 진행 중인 프로젝트: Newsletter v2" | MEMORY.md ✅ | 현재 상태 정보 |

---

### 1-4. 비필수 항목 외부화 프로세스

**판단 기준:** 이 항목이 매 세션 필요한가, 아니면 특정 작업에만 필요한가?

**외부화 절차:**
1. 특정 작업에만 필요한 섹션 식별
2. Claude에게 지시: *"[섹션명]을 루트 CLAUDE.md에서 분리해 새 참조 파일로 이동하고, References 테이블에 1줄 포인터로 교체해줘"*
3. Claude가 자동으로 파일 생성 + 원본 섹션 제거 + 포인터 추가

---

### 1-5. CLAUDE.md 진단 프롬프트 (즉시 사용 가능)

```
내 루트 CLAUDE.md와 MEMORY.md를 검토해줘.

CLAUDE.md에서는: 행동을 지시하는 게 아니라 사실이나 상태를 기록하는 항목을 찾아 플래그해줘.
MEMORY.md에서는: 사실을 기록하는 게 아니라 행동 방식을 지시하는 항목을 찾아 플래그해줘.

각 플래그된 항목이 어디로 이동해야 하는지 추천해줘.
```

### 1-6. Rules 고급 패턴 — 판단 품질 강화

"always / never" 행동 가드레일만으로는 두 가지를 못 막는다 — Claude가 사용자 의견에 그냥 동조하는 것, 그리고 되돌릴 수 없는 행동을 확신도만으로 밀어붙이는 것. Rules 섹션에 아래 두 패턴을 추가하면 판단의 질이 달라진다.

**패턴 1 — 동조 방지 (Push-back Rule)**

Claude가 무조건 동의하지 않고 아이디어의 허점을 능동적으로 찾도록 지시한다.

```
- 내 아이디어나 계획에 무조건 동의하지 않는다. 허점·리스크·반대 사례를 먼저 찾은 뒤 의견을 말한다.
- 칭찬으로 응답을 시작하지 않는다 ("좋은 질문입니다" 류의 검증 문구 금지).
```

더 강하게 적용하려면, 신뢰하는 전문가 여러 명의 관점을 시뮬레이션해 다각도로 비판적 검토를 받는 **"Ask the Board" 스킬**을 별도로 만들고, Rules에는 언제 그 스킬을 호출할지만 명시한다 — 전략적이거나 되돌리기 비싼 결정에 한정한다. 매 응답마다 걸면 속도만 떨어지고 효과는 사라진다.

**패턴 2 — 비가역 행동 확인 게이트 (One-way Door Rule)**

모든 행동이 같은 무게가 아니다. 되돌릴 수 있는 결정(양방통행 문)과 되돌릴 수 없는 결정(일방통행 문)을 구분해, 후자에는 확신도와 무관하게 명시적 확인을 요구한다.

```
- 제안하는 모든 행동을 먼저 분류한다 — 되돌릴 수 있는가(양방통행 문), 없는가(일방통행 문)?
- 일방통행 문(예: 실제 게시·발송, 삭제, 결제, 프로필·설정 변경)은 확신도가 높아도
  반드시 명시적 승인을 받은 후에만 실행한다. 확신은 승인을 대체하지 않는다.
```

이 워크스페이스에 이미 "승인 게이트" 목록이 있다면 이 규칙을 그 목록에 편입시키고, 없다면 이 규칙이 그 시작점이 된다.

### 1-7. 정기 감사 — 규칙 부패(Contextual Rot) 방지

CLAUDE.md는 한 번 잘 정리했다고 끝나지 않는다. 새 규칙을 계속 추가하다 보면 한 달 전 지침("간결하게 답하라")과 어제 지침("상세히 설명하라")이 조용히 충돌한다. 이 충돌은 사용자가 바로 못 느끼고, 결과물 품질이 흔들리는 형태로만 드러난다.

1-5의 진단 프롬프트가 "CLAUDE.md vs MEMORY.md 오분류"를 잡는다면, 이 감사는 **같은 파일 안의 자기모순**을 잡는다. 목적이 달라 둘 다 필요하다.

**실행 주기:** 워크스테이션이나 규칙을 5개 이상 추가했을 때, 또는 최소 분기 1회.

**감사 프롬프트 (즉시 사용 가능):**

```
내 CLAUDE.md와 모든 스킬 파일을 검토해줘.

1. 서로 상충하는 규칙이 있는지 찾아줘 (예: 톤에 대해 다른 지시, 같은 상황에 다른 행동을 요구하는 규칙).
2. 중복되거나 이미 다른 규칙에 포함된 규칙이 있는지 찾아줘.
3. 더 이상 유효하지 않은 낡은 규칙(폐기된 워크스테이션·스킬을 가리키는 것 등)이 있는지 찾아줘.

각 항목에 대해: 무엇이 충돌/중복/낡았는지, 어느 쪽을 남길지 추천안, 근거를 함께 제시해줘.
발견한 것을 곧바로 고치지 말고 먼저 목록으로만 보고해줘.
```

**충돌을 발견했을 때 원칙:** Claude가 조용히 하나를 골라 지우지 않는다. 두 규칙을 나란히 보여주고 어느 쪽이 최신 의도인지 사용자에게 확인받은 뒤에만 반영한다 — 임의로 고르면 다음 감사에서 또 다른 드리프트를 만들 뿐이다.

## SOP 2 | MEMORY.md 작성 및 최적화

### 2-1. 핵심 원칙: 150줄 상한선

루트 MEMORY.md도 **매 세션 로드**된다. 구조화된 경량 파일이 아웃풋 품질을 직접적으로 높인다.

| 기준 | 상태 |
|---|---|
| ~100줄 | ✅ 이상적 |
| 100~150줄 | ⚠️ 모니터링 필요 |
| 150줄 초과 | 🚨 즉시 압축 + 아카이빙 (상한선 올리기 금지) |

---

### 2-2. 표준 3섹션 구조

```
# MEMORY.md

*Last updated: [date]*

## Active Projects
## Scheduled Tasks
## Core Memory
```

**① Active Projects**
- 현재 진행 중인 프로젝트 목록 + 짧은 상태 메모
- 세션 시작 시 Claude가 즉시 컨텍스트 파악 가능
- 완료 시 "archive this" 명령으로 ARCHIVE.md로 이동

**② Scheduled Tasks**
- 자동화된 반복 작업 목록
- 목적: Claude가 중복 스케줄 생성 방지 + 기존 작업 누락 방지

**③ Core Memory**
- 변하지 않는 개인 사실들 (LinkedIn URL, 사업자 주소, 핵심 툴 등)
- 자주 참조되지만 매번 설명할 필요 없는 정보

---

### 2-3. 엔트리 포맷 규칙

모든 MEMORY.md 항목은 다음 형식을 따른다:

- **1~2문장 최대** — 긴 단락 금지
- **날짜 포함 권장** (상태성 항목의 경우): `[2026-05]`
- **상태 뱃지 사용 권장**: `[진행중]`, `[완료]`, `[보류]`

**나쁜 예:**
```
뉴스레터 프로젝트는 2026년 3월에 시작했고 현재 구독자 수를 늘리기 위해
여러 전략을 테스트 중이며 최근에는 LinkedIn 배포를 추가했고 오픈율은
평균 32%를 기록하고 있다.
```

**좋은 예:**
```
- **Newsletter [진행중]** — LinkedIn 배포 추가 완료, 오픈율 32% [2026-05]
```

---

### 2-4. ARCHIVE.md 구조 (3계층 메모리 시스템)

```
루트 MEMORY.md (화이트보드)
    → 활성 프로젝트·핵심 사실 (150줄 상한)
    → 150줄 도달 시 → ARCHIVE.md로 압축·이전

ARCHIVE.md (파일 캐비닛)
    → 완료된 프로젝트·과거 결정·히스토리
    → 매 세션 로드 안 됨 → 토큰 비용 없음
    → 크기 제한 없음 (무제한 보존 가능)
    → 트리거: "3개월 전 X 프로젝트 어떻게 됐어?" 같은 질문 시 로드

워크스테이션/프로젝트별 MEMORY.md (서브 노트)
    → 루트 MEMORY.md를 경량으로 유지하는 핵심 장치
    → 루트: 프로젝트 존재 확인 → 워크스테이션 MEMORY.md: 세부 정보 로드
```

**ARCHIVE.md 세팅 프롬프트:**

```
내 워크스페이스에 ARCHIVE.md 파일을 생성해줘. 그리고:
1. 루트 CLAUDE.md의 Memory System 섹션에 메모리 규칙을 추가해줘:
   - 모든 메모리 항목은 1~2문장 최대
   - 루트 MEMORY.md 150줄 상한선: 상한 도달 시 항상 압축+아카이빙으로 해결
2. 어떤 항목을 MEMORY.md에 유지하고 어떤 항목을 ARCHIVE.md로 이동할지 기준도 알려줘.
```

### 2-5. 캐스케이딩 메모리 구조 (고급)

루트 MEMORY.md가 100줄 이하를 유지하는 핵심 비결:

```
루트 MEMORY.md
  └─ "Newsletter WS 진행중 [활성]" (1줄 포인터)

워크스테이션 MEMORY.md (Newsletter/)
  └─ 노션 페이지 링크
  └─ 이메일 제목 히스토리

  └─ 현재 상태 상세
```

각 워크스테이션과 프로젝트에 개별 MEMORY.md를 두면 루트 파일은 인덱스 역할만 한다.

3. **결과 확인**
   - 워크스테이션 폴더 생성 확인
   - CLAUDE.md 워크플로우 적절성 검토

   - 루트 CLAUDE.md Routing Map 업데이트 확인

## SOP 4 | Workstation vs Skill 결정 프레임워크

### 4-1. 핵심 질문

> **"이것은 내가 일하는 공간인가, 아니면 내가 실행하는 반복 작업인가?"**

| 기준 | Workstation | Skill |
|---|---|---|
| **정의** | 내가 일하는 공간 | 내가 반복 실행하는 작업 |
| **의사결정** | 중간에 판단 필요 | 체크리스트 실행, 자동화 가능 |
| **컨텍스트** | 시간이 지나며 축적 | 실행할 때마다 독립적 |
| **아웃풋** | 매번 다름 (콘텐츠에 따라) | 매번 동일한 구조 |
| **예시** | Newsletter WS, Research Desk | Subject Line 생성, 워크스테이션 감사, 파일 분류 |

### 4-2. 결정 트리

```
이 작업에 중간에 내 판단이 필요한가?
    │
    ├── YES → Workstation
    │         (지속적인 컨텍스트, 의사결정 포인트 있음)
    │
    └── NO → 매번 동일한 아웃풋 구조를 원하는가?
                 │
                 ├── YES → Skill
                 │         (체크리스트, 자동화 가능)
                 │
                 └── NO → References 파일로 충분
```

### 4-3. 실전 예시

**Workstation이 맞는 경우:**
- "이번 주 뉴스레터 작성" → 어떤 주제? 어떤 앱? 어떤 각도? → 판단 필요 → Workstation
- "클라이언트 제안서 작업" → 클라이언트 특성, 예산, 전략 → 판단 필요 → Workstation

**Skill이 맞는 경우:**
- "뉴스레터 제목 5개 생성" → 드래프트 넣으면 항상 동일한 포맷으로 5개 출력 → Skill
- "워크스테이션 감사 리포트" → 항상 Executive Summary + Findings + Recommendations 구조 → Skill
- "파일 PARA 분류" → 파일 목록 넣으면 항상 Projects/Areas/Resources/Archive로 분류 → Skill

## SOP 5 | 워크스테이션 표준 구조

새 워크스테이션 생성 시 반드시 포함할 3가지:

### 5-1. Workstation CLAUDE.md 구조

```markdown
# [워크스테이션명] CLAUDE.md

## Identity
(이 워크스테이션이 다루는 영역, 라우팅 조건, 제외 범위 — 1단락)

## Resources
| Resource | Read when... |
|---|---|
| (온디맨드 로드 파일 목록) | |

## Workflow
1. (주요 작업의 단계별 프로세스)
2. ...

## Editorial Rules
- 00_Resources의 voice-principles.md 준수
- (도메인별 추가 규칙)
```

### 5-2. Workstation MEMORY.md 구조

```markdown
# [워크스테이션명] Memory

## Contacts
(이 도메인 관련 인물 목록)

## Key Decisions
(주요 결정 사항 및 그 이유)

## Current Status
(현재 상태 및 진행 상황)
```

### 5-3. Resources 폴더

- 워크스테이션 생성 시 빈 폴더로 시작
- 작업하면서 참조 파일 추가 (스타일 가이드, 과거 예시, 브랜드 가이드 등)

## 진단 체크리스트

새 워크스페이스 또는 기존 워크스페이스 검토 시 활용:

```
[ ] 루트 CLAUDE.md가 300줄 이하인가?
[ ] CLAUDE.md에 6섹션 구조가 갖춰져 있는가?
[ ] Routing Map에 모든 워크스테이션이 등록되어 있는가?
[ ] 매 세션 불필요한 항목이 외부 참조 파일로 분리되어 있는가?
[ ] CLAUDE.md에 사실(fact)이 아닌 행동 규칙만 포함되어 있는가?
[ ] Rules에 동조 방지(비판적 검토) 규칙이 있는가?
[ ] Rules에 비가역 행동(게시·발송·삭제·결제·설정 변경 등) 확인 게이트가 있는가?

[ ] 루트 MEMORY.md가 150줄 이하인가?
[ ] MEMORY.md에 3섹션 구조(Active Projects / Scheduled Tasks / Core Memory)가 있는가?
[ ] 각 항목이 1~2문장으로 간결하게 작성되어 있는가?
[ ] MEMORY.md에 행동 지시가 아닌 사실만 포함되어 있는가?
[ ] ARCHIVE.md가 존재하는가?
[ ] 색·비율·레이아웃 규칙이 마크다운에만 갇혀 있지 않은가? (시각 규칙은 HTML 레퍼런스 권장)

[ ] 각 워크스테이션에 개별 MEMORY.md가 있는가?
[ ] Workstation과 Skill이 목적에 맞게 구분되어 있는가?
[ ] 더 이상 활성화되지 않은 Claude Projects가 Cowork으로 이전되었는가?
[ ] 최근 분기 내 규칙 상충·중복·낡음 감사(1-7)를 실행했는가?
```
